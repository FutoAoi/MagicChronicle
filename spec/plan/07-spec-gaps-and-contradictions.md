# 仕様不足・矛盾・要決定事項

- 文書版: 0.1.0
- 判定基準: 公開資料同士の不一致、実装が先行した未承認規則、受け入れ条件を作れない空白

## P0 — 実装・テストの正本として先に決める

| ID | 論点 | 現状 | 推奨する決定 | 決めない場合の影響 |
|---|---|---|---|---|
| GAP-P0-001 | 弾・発火の解決順 | 分裂、同時接触、破壊時効果、死亡の順がない | 安定IDを持つ単一`ResolutionQueue`、移動/発火/耐久/破壊/分岐/命中の順を例付きで固定 | 同じ盤面でも実装順で結果が変わり、previewとtestが成立しない |
| GAP-P0-002 | カードゾーン | 捨て札・除外・盤面の移動が未定。実装はexhaustを再投入 | 5ゾーンと全遷移を状態図で承認。各カードは同時に一ゾーン | 進行停止、無限再利用、デッキ枚数不整合 |
| GAP-P0-003 | ターンとコスト | コスト回復、未使用分、複数配置、敵行動順がない | ターン開始時に最大まで回復、配置ごと支払い、持越しなし等を明文化 | バランス値を比較できない |
| GAP-P0-004 | バフ共通契約 | 消費契機がドロー時/敵攻撃後/毎ターン/個別で混在 | 各状態に式、対象、付与、重複、上限、消費契機、寿命、表示を必須化 | 説明と実処理が乖離する |
| GAP-P0-005 | run lifecycle | 新規/再開/敗北/放棄/クリアの初期化・持越しがない | immutable初期定義とruntime stateを分け、遷移ごとのreset表を承認 | 前runのdeck/money/buffが漏れる |
| GAP-P0-006 | 勝敗・死亡 | HP0後のrun終了、引分、複数敵、報酬保持が未定 | EncounterResultとRunResultを分け、勝利・敗北を冪等に確定 | 二重報酬、進行不能、物語分岐不能 |
| GAP-P0-007 | 敵情報 | 共有盤面を使うが意図・射線・対象規則がない | 敵弾の起点・方向・回数を原則完全予告。特殊な伏せは明示タグ化 | 固有の読み合いが理不尽さへ反転 |
| GAP-P0-008 | TGS試遊範囲 | PC/iOS/AndroidとTGS 2026が併記され、優先release gateがない | TGS buildはPC横持ち・1ラン20分等、提出スコープを固定。モバイルは次ゲートに分離 | 3プラットフォーム対応がコア改善を圧迫 |

## 公開資料内の矛盾

| ID | A | B | 整理案 |
|---|---|---|---|
| CON-001 | 筋力は`+1` | スタック加算または倍率として読める | 加算値と倍率状態を別名にし、計算順を固定 |
| CON-002 | バフ回数はカードドロー時に減る | 敵攻撃直後／毎ターン／個別トリガーでも減る | 共通一括減少を廃止し、状態定義ごとのTriggerへ統一 |
| CON-003 | カウンターは被ダメージ割合返却 | 反射は弾の向きを反転させる案 | `反撃`と`弾反射`を別効果・別UIにする |
| CON-004 | テクニカルはカード効果再発動 | テクニカルは毒弾付与 | ビルド軸名を上位タグにし、`再演`と`毒術`を別能力へ分ける |
| CON-005 | コストマイナスはプレイヤーデバフ | カードの必要コスト軽減とも読める | `最大配置力低下`と`カード軽量化`へ改名 |
| CON-006 | 霊陣は破壊時だけ発火 | 通過時効果一覧にも混在し得る | `OnEnter`を持たず`OnDestroyed`だけを持つ定義として固定 |
| CON-007 | 拠点ショップは解放ガチャ | 永続セーブ・恒久通貨・確率仕様がない | TGS版はガチャを外し、図鑑解放または固定アンロックで代替 |
| CON-008 | 企画目標は「無限に遊べる」 | メタ進行、seed、難易度、日替り、記録が未定 | 横方向解放 + challenge modifier + seed履歴を最小メタにする |

## P2 — 製品化前に決める

- セーブ形式、version、migration、破損復旧、クラウド同期の有無。
- キーボード、ゲームパッド、モバイル、入力再割当。
- safe area、最小タップ領域、文字サイズ、色覚、演出軽減、速度変更。
- 対応言語、用語集、文字列外部化、フォントfallback。
- 音量カテゴリ、BGM遷移、フォーカス喪失、振動。
- clean buildに必要なCRIWARE/Spine等の取得、version、checksum、license。
- 分析、クラッシュレポート、プライバシー、課金を採用する場合の法務要件。

## 仕様精査の結論

企画の核と遊びの差別化は明確だが、現在の仕様は「何が起きるか」の候補集であり、「競合した時にどの順で、どの状態を、いつまで変えるか」という実行契約が薄い。P0の8件を決めるまでは、カードや敵を増やすほど実装差分と説明差分が増える。特に解決順、カードゾーン、run lifecycleの3件を先行させる。
