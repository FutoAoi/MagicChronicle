00. エグゼクティブサマリ

総合判断

MagicChronicleは、自分と敵が同じ魔法陣を使う共有盤面と、耐久消滅によって解決途中に経路が変わる時系列パズルに、明確な独自性がある。カードの相乗効果を数値だけでなく弾道として見せられるため、「ピースがはまった時の爆発的な爽快感」という企画意図とも整合する。

一方、現状はルールの正本、カード状態遷移、run初期化、予測UI、自動テストが不足している。実装には回復不能、消耗カード再投入、空山札参照というコアループ直結のHigh不具合が残る。総合評価はAI Format B、リリース判断はHoldである。

面白さと奥深さ

  • 強み: 配置一手が、自弾の大連鎖と敵弾の危険を同時に作る。
  • 強み: 耐久が発火回数、盤面寿命、破壊時価値を一つに接続する。
  • リスク: 分岐、複数弾、状態、破壊、敵turnの順序が見えないと、奥深さではなく予測不能になる。
  • 改善原則: 本質的な複雑さを削らず、暗黙順序・用語不一致・分散状態という偶発的複雑さを下げる。

売れる可能性

Vitiaでは、感覚的実演を重視するLuxuriaが0.768で主軸となった。現段階で最も強い訴求は、次の15秒episodeである。

置く → 連鎖する → 魔法陣が砕けて道が変わる → 敵弾が同じ盤面を逆利用する

「無限に遊べる」「PC/iOS/Android対応」はまだ証拠がなく、訴求に使わない。実gameplayによる短いproofと3分試遊で、qualified demo start、wishlist、内容理解、trustを同時に検証する。

2. シーンと画面遷移

公開仕様の遷移図には、タイトル、拠点、チュートリアル、ステージセレクト、インゲーム、イベント、エンドシーンに加え、オプション、クレジット、図鑑、ショップ、デッキ、山札等のパネルがある。

2.1 タイトル

  • 画面クリックまたはタップで拠点へ移る。
  • 右上にオプションとクレジットを置き、対応パネルを開く。

2.2 拠点

  • 古代遺跡が点在する背景を用いる。
  • タイトル、図鑑、ショップ、出撃準備へ移動できる。
  • 図鑑はカードとキャラクター／敵の一覧を表示する。
  • ショップはキャラクター解放とカード解放ガチャを扱う案がある。
  • 出撃準備からキャラクター選択、チュートリアル、ステージセレクトへ進む。

2.3 ステージセレクト

  • 分岐マップで接続済みの次ルームを選ぶ。
  • ルーム種別はノーマル、エリート、ボス、イベント、ショップ、鍛冶。
  • ショップは回復・カード購入、鍛冶はカード強化を提供する案がある。
  • 現在地にキャラクターアイコンを表示する。
  • オプションと魔法陣デッキ確認パネルを開ける。

2.4 インゲーム

公開仕様にはドロー、配置、攻撃、報酬、カード周りの見出しだけがあり、詳細はゲームシステム資料と実装観測から補う。

2.5 イベント／チュートリアル／エンドロール

画面別仕様は未記載である。イベント題材の候補だけが存在するため、選択肢、コスト、結果、再訪、ラン状態への反映を決める必要がある。

3. 戦闘盤面

  • 中央に5x5の配置マスを持つ。
  • プレイヤーは手札から魔法陣をドラッグして配置する。
  • 配置はコスト制であり、無制限には置けない。
  • プレイヤーの魔法弾は盤面左側から直進を開始する。
  • 魔法弾が魔法陣へ触れた瞬間に、その魔法陣の効果を適用する。
  • 効果は方向転換、分裂、ダメージ、状態異常、ドロー、回復、通貨、耐久操作等を含む。
  • 魔法陣は発動ごとに耐久を消費し、0になった時点で消える。
  • 破壊後、その位置は後続の魔法弾へ影響しない。
  • プレイヤー攻撃後に敵が攻撃し、敵の魔法弾でも同じ魔法陣が発動する。

4. ターン進行

現資料から確定できる最小フローは次のとおり。

  1. ターン開始・ドロー。
  2. 魔法陣の配置。
  3. 配置終了を確定。
  4. プレイヤーの魔法弾を解決。
  5. 敵の魔法弾を解決。
  6. ターン終了効果と継続状態を更新。
  7. 勝敗未決なら次ターンへ進む。
  8. 勝利なら報酬を選び、ステージセレクトへ戻る。

question: 複数弾の同時性、分裂弾の順序、同一魔法陣への同フレーム接触、霊陣と耐久0の処理順、敵が複数いる時の行動順は未定義である。

5. カードとデッキ

  • カードは魔法陣の配置に用いる。
  • ステージクリア報酬で新しいカードを獲得し、ラン内デッキを構築する。
  • カードにはコスト、効果、耐久、方向や分裂等のパラメータがある。
  • 報酬は複数候補から選ぶ画面案がある。
  • 鍛冶でカードを強化する案がある。

未決定のデッキ契約

  • 初期手札、毎ターンドロー数、手札上限。
  • 山札切れ時の再構築と、捨て札・消滅札の区別。
  • 配置済みカードがいつどこへ移るか。
  • 報酬スキップの価値、カード削除、レアリティ、強化上限。
  • ラン終了時のデッキ初期化と恒久アンロックの関係。

7. バフ・デバフ

7.1 効果候補

  • 筋力: 魔法の攻撃力を上げる。
  • 疲労: 魔法の攻撃力を50%下げる。
  • 弱体: 被ダメージを50%増やす。
  • 毒: ターン終了時にスタック分のダメージを与える。
  • 再生: ターン終了時に回復する。
  • カウンター／反射: 受けた攻撃の一部を返す案、または弾を跳ね返す案が併存する。
  • コスト増減: 使用可能コスト最大値を変える。
  • 追加カード: ターン開始時ドロー数を増やす。
  • 連続: 魔法弾の発射回数を増やす。
  • コンボ: 移動マスごとに攻撃力を増やす。
  • バーサーカー: 自傷をトリガーに筋力または怒りを得る。
  • テクニカル: カード効果の再発動案と、毒弾付与案が併存する。

7.2 仕様矛盾

  1. 消費型バフの回数減少が「カードドロー時」「敵攻撃直後」「毎ターン」「特定トリガー」と資料ごとに異なる。
  2. 筋力は +1、スタック分加算、倍率の読み方が混在する。
  3. カウンターはダメージ割合返却、反射は弾反転として分離すべきか不明である。
  4. テクニカルは効果再発動と毒付与で別能力として記述されている。
  5. コストマイナスはプレイヤーへのデバフか、カードコスト軽減か名称から誤読しやすい。

承認されるまで、これらを実装の正本として扱わない。

結論

MagicChronicleの遊びは、次の三層を一つの戦闘へ重ねた設計である。

  1. 盤面パズル — 5x5盤面へ魔法陣を配置し、軌道・順序・耐久変化を設計する。
  2. デッキ構築 — 手札、山札、コスト、報酬選択によって解法候補を組み替える。
  3. ローグライト・ラン — 分岐する部屋を進み、一時的な成長とリスクを管理する。

固有の魅力は、魔法陣の破壊で解決途中にも経路が変化することと、敵弾も同じ盤面・魔法陣を利用することにある。この二点が「自分で組んだ連鎖が爆発する爽快感」と「強い盤面ほど危険にもなる読み合い」を同時に作る。

system:board-card:opponent-assist高・反転敵弾も自分の魔法陣を利用利益と危険の予測表示

三つのループ

戦闘内ループ（秒〜分）

手札確認 → 配置・経路予測 → 自弾を解決 → 盤面変化を確認 → 敵弾を解決 → 次の配置判断

判断の核は「今の最大火力」だけではない。耐久を消費して敵フェーズ前に魔法陣を消すか、敵にも作用する形で残すかがトレードオフになる。予測表示が弱い場合、この判断は奥深さではなく不可解さになる。

ラン内ループ（分〜時間）

部屋選択 → 戦闘・イベント → 報酬選択 → デッキ／バフ更新 → 次のリスク選択 → ボス

ビルドの方向が早期に見え、途中で修正でき、ボスで成果を試せる構造が必要である。現仕様は部屋種別とビルド案を持つが、報酬テーブル、希少度、削除・強化、エリート報酬差が未定である。

メタループ（複数ラン）

発見 → 図鑑・解放 → 新しい初期条件 → 別のビルド探索

企画目標「無限に遊べる」を支える層だが、現資料では最も薄い。単純な恒久強化は難易度を摩耗させるため、横方向の解放、チャレンジ条件、履歴・seed共有を優先する。

UX成果との対応

Ludusの情報・UI、フィードバック観点から、最低限必要な表示は次である。

  • 配置前に自弾と敵弾の予定経路を色分けする。
  • 魔法陣ごとの残耐久、次回接触で消えるか、破壊時効果を盤面上で読む。
  • 分岐・多重発火の解決順を番号またはタイムラインで確認できる。
  • カード移動先を「山札／手札／捨て札／除外／盤面」で一貫表示する。
  • ダメージ、状態、耐久変化を同時に埋もれさせず、因果のまとまりで演出する。
  • 失敗後に「どの弾が、どの魔法陣を経て、なぜ被害になったか」を短く振り返れる。

強み

  • 盤面を自分と敵が共有するため、攻撃装置と防御上の危険が同じオブジェクトに宿る。
  • 耐久による消滅が、固定パズルではなく時系列パズルを生む。
  • デッキ構築のシナジーを、数値だけでなく弾道の見た目として表現できる。
  • 一手の準備が多段連鎖へ変わるため、企画の「ピースがはまった時の爆発的爽快感」と整合する。

主なリスク

  1. 予測不能化 — 解決順、分岐、敵弾、耐久消滅が重なり、理解より先に結果が出る。
  2. 層の競合 — パズル最適解がデッキ選択を無意味にする、またはドロー運が盤面思考を上書きする。
  3. 敵ターンの理不尽さ — 同一盤面の利用が魅力である一方、敵意図と射線が不明なら罰に見える。
  4. ランの単調化 — 部屋と報酬の差が小さい場合、同じ戦闘の反復になる。
  5. 恒久成長の未定義 — 「無限に遊べる」を支える再訪理由がない。

優先して仕様化する決定

  1. 発火・分岐・破壊・死亡を含む単一の解決キュー。
  2. 山札、手札、捨て札、除外、盤面の状態遷移。
  3. 自弾と敵弾の完全予測／部分予測の境界。
  4. バフの寿命、消費契機、重複、上限、無効化順。
  5. ラン終了時に失うもの、残るもの、次のランで増える選択肢。
  6. 連鎖の巧さを測るゲーム内評価と、爽快感を検証するプレイテスト指標。

1. Run Progression

ラン開始から終了までの状態、マップ、部屋遷移を所有する。

集約・値

  • Run: RunId、seed、難易度、現在階層、現在部屋、状態、ラン内資産。
  • RunMap: 階層とRoomNodeの有向非巡回グラフ。
  • RoomNode: 種別、接続先、公開情報、解決状態。
  • RunState: NotStarted / SelectingRoom / ResolvingRoom / Rewarding / Cleared / Failed / Abandoned。

コマンドとイベント

  • StartRun(seed, character, startingDeck) → RunStarted
  • SelectRoom(nodeId) → RoomEntered
  • CompleteRoom(result) → RoomCompleted, RewardOffered
  • FailRun(reason) → RunFailed

不変条件

  • 現在ノードから接続された未解決ノードだけを選択できる。
  • 一つの部屋を二重に解決しない。
  • Cleared / Failed / Abandoned後にラン内状態を変更しない。

2. Combat Encounter

一回の戦闘、ターン、弾の解決、勝敗を所有する。

集約・値

  • Encounter: 参加者、盤面、ターン番号、フェーズ、解決キュー、結果。
  • Combatant: HP、最大HP、攻撃起点、状態。
  • TurnPhase: Planning / PlayerResolution / BoardSettling / EnemyResolution / EndTurn / Reward / Finished。
  • Projectile: 所有者、位置、方向、威力、タグ、残り分岐履歴。
  • EnemyIntent: 次の射出点、軌道に影響する情報、予告精度。

コマンドとイベント

  • CommitPlacement(plan) → PlacementCommitted
  • ResolvePlayerProjectiles() → ProjectileAdvanced, MagicCircleTriggered, DamageApplied
  • ResolveEnemyProjectiles() → 同上
  • AdvancePhase() → PhaseChanged
  • ConcedeEncounter() → EncounterLost

不変条件

  • フェーズ遷移は一方向で、解決中に新しい配置を受け付けない。
  • 勝敗確定後はダメージ、回復、報酬を二重適用しない。
  • 全ての結果は決定的な解決キューから順に生成する。

3. Board Topology

5x5盤面、魔法陣、接触、方向変更、分岐、耐久を所有する。このドメインが本作の中核である。

集約・値

  • Board: 幅5、高さ5のCell集合。
  • Cell: 座標、地形、配置物。
  • MagicCircleInstance: 定義ID、向き、残耐久、所有、付与修正。
  • Route: Projectileが通った座標と発火列。
  • ResolutionQueue: 安定した順序を持つドメイン操作列。

コマンドとイベント

  • PlaceMagicCircle(cardInstanceId, coordinate, rotation) → MagicCirclePlaced
  • EnterCell(projectileId, coordinate) → MagicCircleTriggered
  • ChangeDirection, SplitProjectile, ChangePower
  • ConsumeDurability(amount) → DurabilityChanged, MagicCircleDestroyed

解決規則の提案

  1. Projectileが次セルへ入る。
  2. セル上の魔法陣を一度だけ発火予約する。
  3. 発火効果をカード記載順、同順位なら安定ID順でキューへ積む。
  4. 効果を一件ずつ適用し、その発火の耐久を消費する。
  5. 耐久0なら破壊イベントをキュー末尾へ積む。
  6. 分岐弾は親弾の直後へ、方向の安定順で積む。
  7. 盤外・停止・対象命中まで繰り返す。

正式仕様では、破壊時効果と次の弾のどちらが先か、同一魔法陣への再入場、無限ループ上限を決定する必要がある。

不変条件

  • 一つのセルに置ける盤面オブジェクト数は仕様上限以下。
  • 耐久は0未満にならず、0の魔法陣は後続弾へ作用しない。
  • 同じ入力、seed、初期状態から同じイベント列を得る。
  • 一つのProjectileに発火数または移動数の安全上限を置く。

4. Deck & Build

カードの定義とインスタンス、各ゾーン、ドロー、配置コスト、報酬によるデッキ変更を所有する。

集約・値

  • DeckBuild: 所有カードインスタンスとラン内修正。
  • CardDefinition: 表示名、コスト、タグ、魔法陣定義、基礎効果。
  • CardInstance: 一意ID、強化段階、ラン内修正。
  • CardZone: DrawPile / Hand / DiscardPile / Exhausted / Board / RewardOffer。
  • BuildTag: Combo / Berserker / Technical / Spirit等。

状態遷移

stateDiagram-v2
  [*] --> DrawPile
  DrawPile --> Hand: draw
  Hand --> Board: place and pay
  Hand --> DiscardPile: discard
  Board --> DiscardPile: combat rule
  Board --> Exhausted: exhaust rule
  DiscardPile --> DrawPile: reshuffle
  RewardOffer --> DrawPile: acquire
  Exhausted --> [*]: end of run

不変条件

  • 一つのカードインスタンスは同時に一つのゾーンにだけ属する。
  • コスト不足なら配置確定しない。
  • 山札再構築は捨て札を一度だけ移し、空のままならドローを終了する。
  • 除外カードを通常の捨て札へ戻さない。

5. Effects & Status

魔法陣効果、バフ、デバフ、トリガー、スタック、寿命を統一して所有する。

集約・値

  • EffectDefinition: 対象、契機、演算、優先度、タグ。
  • StatusInstance: 定義ID、付与先、スタック、残回数、残ターン。
  • Trigger: OnPlace / OnProjectileEnter / OnDestroyed / OnDamage / OnDraw / OnEnemyAttack / OnTurnEnd。
  • Modifier: 加算、乗算、置換、禁止。

不変条件

  • 全状態に消費契機と寿命を必須とする。
  • 同名状態の重複規則をAdd / Refresh / Replace / Rejectから選ぶ。
  • 置換・禁止・乗算・加算の順を固定する。
  • UI文言と実際の契機は同じ定義から生成する。

6. Economy & Reward

ラン内通貨、報酬候補、店、鍛冶屋、価格、支払いを所有する。

集約・値

  • RunWallet: 通貨種別と残高。
  • RewardOffer: 候補、選択数、期限、取得済み状態。
  • ShopInventory: seed付き商品列、価格、売切れ状態。
  • UpgradeOffer: 対象カード、変化内容、価格。

不変条件

  • 支払いと取得は一つの操作として成功または失敗する。
  • 同じ報酬を二重取得しない。
  • 価格は購入前に確定し、表示値と決済値を一致させる。
  • 通貨の発生源と消費先をイベントとして追跡できる。

7. Meta Progression

複数ランを跨ぐ発見、解放、図鑑、チャレンジを所有する。

集約・値

  • PlayerProfile: バージョン、解放、実績、設定参照。
  • Collection: 発見済みカード・敵・イベント。
  • Unlock: 条件、対象、受領状態。
  • Challenge: 制約、記録、報酬。

恒久成長は数値強化より、初期デッキ、キャラクター、カードプール、チャレンジなど横方向の選択肢を優先する。これは「無限に遊べる」と難易度維持の両立に向く。

8. Narrative Content

イベント、選択肢、物語フラグ、エンディング条件を所有する。

集約・値

  • NarrativeEvent: 出現条件、本文、選択肢、効果。
  • StoryFlag: ラン内／プロフィール内のスコープ。
  • EndingCondition: Chronicle撃破、Kairos解放、隠しボス等の判定。

不変条件

  • 選択可能な選択肢が0件のイベントを開始しない。
  • 不正なIDでも画面を閉じられる安全なフォールバックを持つ。
  • 文言、条件、効果を同じコンテンツIDで追跡できる。

メカニクスの核

本作の最小プレイヤー動詞は三つである。

  1. 読む — 手札、盤面、耐久、敵意図、残資源を読む。
  2. 置く — カードをコストと位置・向きへ変換する。
  3. 確定する — 自分では直接操作しない弾道解決を見届け、次の状態を受け入れる。

本作固有の面白さは配置→結果ではなく、一つの配置が、耐久消費を介して時間順に別の盤面へ変わることにある。敵弾が同じ装置を通るため、プレイヤーは火力、寿命、安全性を一つの配置で同時に最適化する。

主要な経済循環

1. コスト循環

ターン開始で供給 → カード配置で消費 → 盤面価値へ変換 → ターン終了でリセット

設計として最も理解しやすい短期循環になり得る。未使用分の持越し、最大コスト、軽減と最大値低下の語彙が未定なため、現時点では閉じていない。

2. 耐久循環

カード取得 → 配置時耐久 → 発火で消費 → 破壊または後続弾の経路変化 → ダメージ/資源へ変換

本作で最もきれいな循環である。同じ値が「効果を何回使えるか」「いつ盤面から消えるか」「破壊時効果をいつ得るか」の三役を持つ。ただし三役を画面で同時に読めること、耐久回復が無限連鎖を作らないことが条件になる。

3. カード経済

戦闘勝利 → カード追加 → 選択肢/シナジー増加 → 勝ちやすくなる → さらにカード追加

現状は正のフィードバックに偏る。カード追加が常に報酬ならデッキが肥大し、狙った連鎖を引けなくなるため、見かけ上の報酬が罰へ反転する。スキップ報酬、削除、強化、希少度、ビルドtagによる重みづけがsink/quality converterとして必要である。

4. HP・所持金・部屋選択

戦闘でHPを失う → 高報酬ルートか回復/店を選ぶ → 所持金をHPまたは戦力へ変換 → ボス到達

ローグライト全体の緊張を作る循環だが、回復量、部屋比率、価格、報酬差がないため成立を評価できない。回復が安すぎればHP圧力が消え、高すぎれば店が実質回復専用になる。

5. メタ循環

runで発見/達成 → 横方向の選択肢解放 → 新しい初期ビルド → 別の発見

企画目標「無限に遊べる」に必要だが未実装・未仕様である。恒久火力だけを増やすとパズルの緊張が減るため、キャラクター、初期デッキ、カードプール、challenge modifier、seed履歴を中心にする。

複雑度を奥深さへ変える設計

  1. 配置中に最終ダメージだけでなく、番号付きの発火列を表示する。
  2. 自弾の完全予測を先に教え、敵共有はチュートリアルの次段で解禁する。
  3. 分岐、破壊時発火、状態の各語彙を一度に増やさず、runの階層で導入する。
  4. カード本文をTrigger → Effect → Lifetimeの定型文にする。
  5. 結果後に3秒程度の因果ログを出し、想定外だけを遡れるようにする。
  6. 上級者にはpreview簡略、速度変更、詳細ログを選ばせ、初心者向け支援と同居させる。

数値設計の最小モデル

実装前にスプレッドシートまたはシミュレータで次を持つ。

EncounterBudget = ExpectedPlayerHP * TargetLossRate
CardValue = ExpectedDamage + SurvivalValue + DrawValue + EconomyValue
PlacementEfficiency = CardValue / PlacementCost
DurabilityValue = Sum(ExpectedTriggerValue at trigger n) + DestructionValue
RoomEV = RewardEV - ExpectedHPDamageValue - OpportunityCost
DeckQuality = DrawWeightedSynergyValue - DilutionPenalty

同じ尺度へ無理に全てを換金するのではなく、比較可能な仮想価値としてバランス差分を見る。特に破壊時価値を通常発火価値と別にしないと、耐久0を早めるカードを正しく評価できない。

プレイテスト指標

  • 配置から確定までの中央値、取り消し回数、無操作時間。
  • 予測と実結果が違ったターンの割合と原因。
  • 1ターンの発火数、分岐数、盤面変化数、演出時間。
  • 被ダメージのうち敵意図を理解していた割合。
  • 報酬スキップ率、デッキ枚数、tag集中度、不要札率。
  • 金不足で選べなかった部屋/商品、回復への支出比率。
  • 敗北時に再挑戦したい割合、別ビルドを試した割合。
  • 「自分が連鎖を作った」と答える割合。爽快感の中心KPIとする。

結論

盤面耐久は、空間・時間・経済を一つの値で接続する非常に強いメカニクスである。改善の中心はルールを減らすことではなく、カードゾーン、解決順、状態寿命、run resetを閉じ、予測と因果表示でプレイヤーの所有感を守ることにある。

UXの結論

MagicChronicleのUX目標は、情報を減らすことではなく、プレイヤーが「自分の一手で連鎖を作った」と因果を所有できることである。最大の阻害要因は、弾道、発火順、耐久消滅、敵弾が一度に動き、結果だけが派手に見えることである。

最優先の改善は、配置前の時系列preview、盤面上の残耐久、敵意図、解決後の短い因果ログである。これらは初心者支援であると同時に、上級者が深い最適化を行うための道具になる。

情報優先順位

  1. 現フェーズと確定可能性。
  2. 自弾・敵弾の起点と予定経路。
  3. 発火順と、次の接触で消える魔法陣。
  4. 選択カードのcost、trigger、effect、lifetime。
  5. HP、状態、deck zone。
  6. 予想damage等の集約値。

damage予測だけを出すと学習を奪うため、必ず因果列へ展開できるようにする。

時系列preview

表示モード

  • 簡易: 経路線、最終damage、消滅予定を表示。
  • 詳細: ①接触 → ②分岐 → ③耐久0/破壊 → ④後続弾直進をstep表示。
  • 差分: ドラッグ中は配置前/後で変わった経路だけを強調。
  • 不確実: randomや伏せ情報は範囲・分岐候補として表示し、確定線と混ぜない。

色と形

  • 自弾はcyan実線、敵弾はmagenta破線。色だけに頼らず線種と起点iconを併用。
  • 発火番号は円、破壊は亀裂icon、残存は盾形耐久badge。
  • 有利/不利を赤緑だけで表現せず、+ / −、矢印、patternを併用。

解決演出

連鎖の爽快感を守りながら理解可能にする。

  1. 発射前0.2秒で起点と予定線をpulse。
  2. 一つの因果まとまり（接触→分岐→hit）を視線追従可能な速度で再生。
  3. 同時に多数発火しても、主要chainのdamage数字を一つに束ねる。
  4. プレイヤー入力不可時間が長い場合、1x/2x/4xを常設。
  5. 想定外の被害時だけ、直前3〜5イベントを自動で残す。

演出skipは結果を即時適用しても、因果ログと最終盤面を失わない。

カード文面の標準

[Trigger] 魔法弾が入った時
[Effect] 左右へ1発ずつ分岐する
[Lifetime] 発火後、耐久を1失う（現在 2）
[Tag] コンボ / 分岐

状態は効果量・対象・消費契機・残寿命・stack上限を同じ順で書く。テクニカル等のビルド名を効果名の代わりに使わない。

4. Strategy card

Audience hypothesis: build構築と先読みを好む成人playerは、カードの数値説明より、自分の一手が盤面を変形させて大連鎖になる短い実演に反応する。

Bottleneck: 共有盤面と時系列変化を文章で理解する前に離脱する。

Primary domain / job: Luxuria — 最初の10〜15秒で「置く→連鎖→砕ける→敵弾で反転」のepisodeを体験させる。

Verified feature → outcome → mechanism: 敵味方が同じ魔法陣を発火し耐久で消滅する → 一手が火力とriskを同時に作る → 予測線と連鎖演出を含む短いplayable demoでmental simulationを起こす。

Proposition:

その一手は、最強の連鎖にも、敵の罠にもなる。5×5の魔法陣ローグライト。

Message variants:

  • 置いた魔法陣を、敵の弾まで使ってくる。
  • 道を組め。連鎖させろ。壊れる順まで読み切れ。
  • カードのコンボを、盤面に描く。

Proof: 実gameplayの未編集15秒、入力から最終結果までの一続き。自/敵弾、発火順、耐久が読めるUIを含める。

CTA: 3分で、一本の連鎖を完成させる。試遊後は任意のSteamでフォロー / wishlist。拒否・離脱を容易にする。

Channel and moment: TGS boothのattract loop、試遊待機画面、Steam trailer冒頭、短尺SNS。長いworld説明は後段。

Boundary condition: previewが読めず結果が偶然に見えるbuild、未実装platform、未検証の無限性は訴求に使わない。

5. Experiment

TGS/online動画テスト

  • Control: genre、5x5盤面、deckbuildingを事実として説明する静止/通常動画。
  • Treatment: 同じofferで、共有盤面の15秒episode + 上記proposition。価格や特典は変えない。
  • 対象: 18歳以上、roguelike/deckbuilderへ関心を自己申告した来場者/視聴者。未成年や脆弱性によるtargetingをしない。
  • Primary metric: qualified demo start率。Steam上ではtrailer 15秒到達→wishlist率。
  • Guardrail: demo後の「映像どおりのgameplayだった」trust rating、途中離脱、混乱率、誤期待自由記述。
  • 補助: time-to-first-value、3連鎖達成率、「敵も使う」を説明できる割合。
  • Stopping rule: 各cell最低200 qualified exposureを目安に事前固定し、会場日/導線差を記録。無作為割当できない会場比較は因果と呼ばない。
  • Disconfirming result: start/wishlistが上がっても、因果理解が下がる、trustが悪化する、実playの早期離脱が増える場合は不採用。

  • blocked conditionは現入力にない。七domainは人の人格診断に使っていない。
  • fake scarcity、countdown、人気捏造、shame、hidden defaultを使わない。

1. 企画・仕様の要約

  • source: 一人用roguelike puzzle。5x5盤面へ手札の魔法陣をcostで配置する。
  • source: 自弾が左から進み、接触した魔法陣が方向変更、分岐、damage、状態等を発火する。
  • source: 発火で耐久が減り、0で消滅。後続弾は変化後の盤面を通る。
  • source: player攻撃後、敵弾も同じ魔法陣を発火する。
  • source: 企画conceptは「ピースがはまった時の爆発的な爽快感」「無限に遊べる」。TGS 2026出展を目標とする。
  • source: deckbuilding、分岐map、戦闘/event/shop/鍛冶/elite/boss、三つのbuild軸を想定する。
  • unknown: 完全な解決順、card zone、buff式、run reset、economy値、meta progression、platform gate。

2. Ludus解析の要約

  • analysis: 遊びは盤面puzzle、deckbuilder、roguelite runの三層。
  • analysis: 差別化の中心は、解決途中で盤面が変わる時系列puzzleと、敵も同じ装置を使うrisk/reward。
  • analysis: 強みはsynergyが数値だけでなく弾道として見えること。
  • analysis: 最大riskは予測不能化、draw運と盤面最適解の競合、敵turnの理不尽さ、runの単調化、meta不在。

3. ドメイン整理の要約

人手モデルはRun Progression、Combat Encounter、Board Topology、Deck & Build、Effects & Status、Economy & Reward、Meta Progression、Narrative Contentの8領域。Presentation/Inputはadapterとした。

analysis: 中心となる不変条件は、決定的ResolutionQueue、一card一zone、支払いと取得の原子性、run終了後の不変性、全状態のtrigger/lifetime、同じseed/inputから同じ結果である。

Tensions

T1 深さ vs 可読性

  • Thesis: 共有盤面と耐久消滅は、空間と時間を同時に読む独自の深さを作る。
  • Antithesis: 分岐、複数弾、状態、敵turnが重なると、previewが答えを表示するか、無ければ運に見える。
  • Evidence needed: 予測不一致率、発火列理解、3連鎖到達時間、preview有無の比較。

T2 deckbuilding vs board puzzle

  • Thesis: 引いたcardから毎turn別の経路を作る即興性がreplay価値を作る。
  • Antithesis: 強いboard最適解がcard差を消すか、draw luckがboard思考を上書きする。
  • Evidence needed: card選択多様性、tag集中度、drawによる勝敗寄与、同盤面の解法数。

T3 spectacle vs agency

  • Thesis: 多段連鎖の派手な自動解決はTGS/動画で強い。
  • Antithesis: 長い自動演出はplayer agencyを奪い、「自分が作った」感覚を弱める。
  • Evidence needed: 入力不能時間比、speed利用、chain所有感、映像理解。

T4 differentiation vs scope

  • Thesis: puzzle + deckbuilder + roguelite + story + metaは市場上の厚みになる。
  • Antithesis: 8 domainと3 platformを同時に完成させると、最も売れる共有盤面の質が薄まる。
  • Evidence needed: TGS vertical sliceの成功KPI、残日数、team throughput、feature cut候補。

T5 content量 vs rule engine

  • Thesis: 敵、card、event、bossが多いほどrun varietyが上がる。
  • Antithesis: 今contentを増やすと、未定義ruleとManager cycleが指数的にtest matrixを増やす。
  • Evidence needed: 新card一枚当たりのregression工数、rule coverage、content使用率。

T6 marketable moment vs durable product

  • Thesis: 15秒のchain clipで試遊獲得は可能。
  • Antithesis: clipが売れても、meta progression、economy、run varietyが弱ければretentionとreviewは続かない。
  • Evidence needed: trailer→demo、demo→wishlist、first run→second run、build variety、fatigue。

Positions for debate

  1. Core-first: TGS版はPC、短いrun、共有盤面に絞り、meta/story/mobileを後ろへ送る。
  2. Content-first: 多様なcard/enemy/bossを優先し、見栄えとreplayを先に作る。
  3. UX-first: resolverは現状を保ち、preview/tutorial/演出で理解可能にする。
  4. Architecture-first: contentを止め、ResolutionQueue/RunDeckState/RunStateとtestを先に作る。
  5. Market-first: 15秒proofを先に作り、反応が弱ければ大規模改修前にpositioningを変える。

Decision criteria

  • Unique value: 他作品で代替しにくいか。
  • Player agency: playerが結果を自分の判断として説明できるか。
  • Learnability: TGSの短時間で最初の価値へ届くか。
  • Reliability: core loopが停止せず決定的か。
  • Scope efficiency: 一つの改善がbug、UX、content速度、marketing proofを同時に改善するか。
  • Evidence: 実測可能で、反証条件を持つか。

Initial synthesis hypothesis

hypothesis: 最も効率がよい順は、(1) 3 core bugとcard保存則、(2) deterministic ResolutionQueueの最小版、(3) 発火列preview/tutorial、(4) 15秒proofのplaytest、(5) 反応を見てcontent、(6) meta/mobileである。Architecture-first単独では遅く、UX-first単独では暗黙ruleを固定できないため、resolverの薄い正本化とpreviewを同じvertical sliceで行う。
